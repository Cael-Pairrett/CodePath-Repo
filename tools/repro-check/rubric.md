# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (and, if present, any env line in the claim), read against the dimensions the issue itself names as load-bearing. | A concrete environment record is present that names the tool/subject version and the OS or equivalent platform. When the issue treats an extra dimension as load-bearing (driver, shell, browser + language order, build profile, display/GPU, package manager), that dimension is recorded too. A report with no environment record at all fails. | required |
| steps-followable | The repro report's steps (commands, setup, fixtures), read as a stranger who has only this package. | Steps run from a stated starting state through the trigger with concrete, re-runnable actions and inputs the reader can obtain (inline snippets, public URLs, issue-linked playgrounds, or commands that create the fixture). Fail if a load-bearing setup detail named in the issue is omitted (for example the driver on a Windows/driver-specific bug), or if any essential input lives in a private/unshared repo, config, or monorepo the reader cannot access. | required |
| behavior-matches | The repro report's artifacts (command output, logs, measurements, console/CSS panes, described screenshots) read against the issue body's described actual behavior. | At least one real artifact is present, and it shows the issue's specific reported behavior (same failure mode: the same panic/error class, missing header, wrong query answer, blank pane, lost edit, etc.). An honest cannot-reproduce also passes when its artifacts show the attempted run and the non-matching observation. Fail on pure assertion with no artifact; on setup-only artifacts (version banner, process running, tabs visible) that never show the bug symptom; and on adjacent different failures (arg-validation error vs capacity-overflow panic; unbound-variable compile error vs Invalid path expression; HCL syntax error vs decoder panic; garbled escape text with a live prompt vs a crash). | required |
| env-faithful | The environment record compared to the issue's stated target (version, platform, release channel), plus any explicit delta callout in the report or claim. | The tested version/platform matches what the issue targets, or matches current/latest when the thread is about current behavior, OR every material deviation is called out in plain language (for example "filed on 2.x / main; I tested 1.5.3"). Silent testing on a mismatched older version, wrong channel, or wrong platform that cannot speak to the reported bug fails even if the error text looks similar. | required |
| outcome-honest | The claim comment's and repro report's stated outcome ("reproduced", "crash confirmed", "cannot reproduce", root-cause claims) read against what the artifacts actually show. | The stated outcome matches the artifacts. "Reproduced" / "confirmed" requires artifacts of that behavior. "Cannot reproduce" with a real attempt, shown observation, and named differences is a pass. Fail when prose overclaims the artifact (calling a graceful validation error a crash; saying a live window "crashed"; stating expected/actual backwards from what was shown; asserting a root cause or "I verified the race" with no transcript). | required |
| claim-specific | The candidate claim comment read against this issue's subject. | The claim names this issue's concrete subject and states a modest, specific next intent (what will be investigated or tested next). Fail on me-too / +1 with no intent, on self-assignment with no plan, and on interchangeable assign-me boilerplate that over-promises a guaranteed fast fix and could be pasted onto any issue. | required |
| ai-policy | The repo-facts contribution / AI policy read against the wording of the claim comment and the repro report. | If the policy requires disclosing AI use on issues or comments, at least one of the comments discloses the assistance (tool and extent, or an equivalent clear disclosure). If the policy requires human-authored comments in the contributor's own words (AI-generated comments discouraged or hidden), the comments read as specific human voice for this issue, not generic generated filler. If there is no AI policy, or the policy is permissive without a disclosure or human-voice requirement for issue comments, this check passes. Course packages are treated as AI-assisted work when disclosure is required. | required |

## Verdict rule

Accept if and only if every `required` check is graded `pass`.
`preferred` checks (none in this rubric) never change the verdict.
Treat `unclear` as `fail`: proof that cannot be verified is not ready to post.
A single required fail holds the whole package (`reject`).
